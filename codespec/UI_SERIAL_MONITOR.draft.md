## 1 范围与边界

**本期交付**＝需求原文那两句，逐句对口：

1. **十六进制收发视图**：一只停靠卡片面板，逐行显示该串口会话的**原始字节 run**，每行带方向（RX／TX）与
   十六进制字节；可打印 ASCII 就近显示在尾栏（D5）。
2. **行首时间戳前缀**：每行行首一个 `[HH:MM:SS.mmm]`，取自该 run 到达／写出那一刻（D6）；面板内一枚开关可关掉。
3. **可选**：默认不采集。只有用户在串口标签上唤起过一次面板，那条会话才开始留痕（D7）。
4. 面板动作四个：刷新（自动跟帧）／暂停、清空、时间戳开关、丢弃计数上屏。

**不在本期**（§7 在册）：滚动回溯、导出到文件、复制行到剪贴板、过滤与搜索、逐字节时间戳、报文边界识别
（不做任何协议解析）、把监视扩到本地/SSH/Telnet 三型（机制在 `Session` 上通用，**入口只挂串口标签**）、
真机走查与 Windows 腿验证。

**与既有裁决的交界**：

- **不动 VT / 网格 / 编码腿**：视图吃的是 `Session` 两端的字节，不碰 `decoder_`、不碰 `terminal_`、不碰
  `term::encode_key` 的字节表，也不新开第二套解码器（D5 的「文本档」为什么不做的理由）。
- **不动行尾折算**：TX 采样在 `write_out` 折算之后，因此视图显示的字节与线上逐字节一致（F2），也因此
  「档案选 LF 还是 CRLF」在这张卡上是**看得见的证据**——这正是这条判据的副产品。
- **不落盘**（§4.5 第 24 条同档）：环只在内存，不进会话日志文件、不进崩溃转储、不进配置目录。设备流量
  可能含口令回显，「不持久化」是本件的第一条安全口径，代价是关掉就没了（§7）。
- **不新设置键**（F13）：时间戳开关与显示行上限都是面板局部量；重启后回到缺省档。

## 2 屏面与判据对应

主屏＝左侧停靠卡片（非模态、默认隐藏）。行形态算术（14 pt 等宽、单格 11 dp，F8／F9）：

```
[12:00:00.345] RX  41 42 43 44 45 46 47 48  |ABCDEFGH|
└── 14 ──┘└ 5 ┘ └─────── 23 ───────────┘ └── 12 ──┘  = 54 字符 ≈ 594 dp（末段含分隔两空格与竖线）
```

| 区域 | 判据 | 对应需求子项 |
|---|---|---|
| 标题行 | 「串口监视」+ 绑定的档案名与设备路径 + 字节计数 +「清空」+「关闭」；非串口标签或该格无会话时面板不出现（命令侧先分流） | 十六进制收发视图 |
| 开关行 | 两枚：时间戳前缀（缺省开）、暂停刷新（缺省关）。**缺字段设置键**：都是面板局部量 | 行首时间戳前缀 + 「可选」 |
| 行区 | 每行一条 8 字节的转储行（D5）：`[HH:MM:SS.mmm]` + `RX`/`TX` + 8 组两位十六进制 + 竖线包起的 ASCII 尾栏；等宽族 `kDefaultMonospaceFamily`；RX／TX 只以这两个字母与一列强调色区分，行正文一个中文都不出（面板上的可见文案全走 `settings_label(key)`，否则覆盖闸的表外文件判据当场转红） | 两项 |
| 行边界 | 尾栏只承 ASCII 可打印区（0x20–0x7E），其余字节（0x00–0x1F 与 0x7F–0xFF）一律一个 `.`；十六进制正文一律大写字母 | 视图可读性 |
| 挂起尾段 | 一个 run 里的最后一段没有行尾跟随的字节，不单独成行、也不丢——它与后续 run 拼成同一显示行（F10） | 视图正确性 |

| 空态 | 尚未有任何 run 时行区画一句「等待数据」 | 视图 |

## 3 裁决（D1–D9，推荐档已自决采纳）

| # | 待决 | 选项 | 结论（推荐） | 理由 |
|---|---|---|---|---|
| **D1** | 视图落点 | ① 独立停靠卡片（面板族第 8 只）；② `TerminalView` 里加一档「十六进制模式」把行写进网格；③ 视口角落的常驻浮层 | **①** | ② 在结构上就不成立：TX 字节从不进网格（F12），要显示「发出去的东西」必须先造一套第二网格；而往网格塞假内容会同时污染复制、搜索、`OSC 133` 块表与 scrollback 语义。③ 常驻浮层违背「可选」，且遮挡正在看的设备输出。① 与隧道／片段／SFTP 同族，搬窗、状态泵、观测面三条腿全是现成的（F14） |
| **D2** | 采样落点 | ① 都在 `Session`：RX 取 `ingest` 出锁后那份原始 `bytes`，TX 取 `write_out` 交连接前的字节；② 各连接腿自己记；③ 平台层（`platform::serial`）记 | **①** | ② 要为四型连接各写一遍，其中三型本期没有消费方（AGENTS §4.1 第 3 条不加将来才用的抽象），且 SSH 腿要同时覆盖 shell／SFTP／隧道多条通道，形态完全不同；③ 违反 §4.5 第 23 条（平台假设不得渗入共享路径），而且在平台层就看不到**折算后**的出向字节（F2），行尾那半条判据会失真。① 一处腿、两型出口天然都覆盖 |
| **D3** | 环里存什么 | ① 原始 run（方向 + 一个时间戳 + 字节）；② 折好的显示行文本；③ 只存计数不存内容 | **①** | F7 说 1 MiB 流量折成行文本是 5 MB，而同样 1 MiB 原始字节只有 1 MiB；行文本还会把「视图开关是显示期量」这件事焊死在采集期（改档就得重采、采过的字节就没了）。① 让折算留在面板侧，视图形态可调而采集腿不动 |

## 5 数据流与线程模型

```
读线程 ── on_bytes ──► ingest ──┬── 锁内：decoder_->feed → terminal_.feed → collect_damage
                               └── 出锁第一格：record_raw(Received, bytes)  ← 应答回写之前（§4.2①）
                                   └── 之后才是 flush(应答) → 推队列 → 唤醒 → log append
主线程 ── 键入/粘贴/片段 ──► send_text / send_bytes ──► flush ──► write_out（行尾折算）
                                                                  └── emit_to_connection()：
                                                                      record_raw(Transmitted, 折算后)
                                                                      再 connection_->write(同一份)
主线程 ── on_frame ──► SerialMonitorPanel::tick() ──► snapshot Hook ──► RawTap::snapshot(≤ 环上限)
                                                        └── monitor_rows(...) ──► 行表 diff ──► 有变才重建行区
```

- **未开卡的会话零成本**（五期稿 D41 改判的原句是「非串口会话零成本」）：这条因果本来就与连接类型无关——
  没开过卡就没有 `RawTap` 实例，采集点在那枚空指针上判一次就走（`record_raw()` 的短临界区根本不进）。
  五期把入口从串口一型扩到四型之后，旧那句会在 SSH／Telnet／本地三型上读出「与运行时不符」的文档，故
  连同 `include/borealis/session/raw_tap.h` 的头注一起改判；**行为不变**，武装仍只发生在开卡那一刻。
- **两把锁不相交**：`RawTap` 自有 `mutex_`，`Session::mutex_` 只护状态机与解码器（架构 §3.4「锁内不做 IO」）。
  `record()` 只在**不持** `Session::mutex_` 的上下文里调用，这条写成头注的硬约束，与 `SessionLog::append` 同。
- **latest-value 而不是事件流水**（§4.5 第 25 条）：面板每帧取「环里现在有什么」，丢帧不影响下一帧正确性；
  不做「本帧新增的 run」那种增量协议——那要引入消费游标，而游标一旦与暂停/清空交错就会说出「少了半屏」。
- **拷贝量级**：一次 `snapshot()` 至多交出 256 KiB（D4 的环上界就是快照上界，不需要第二个数）；
  面板先按 run 边界从环尾截走 `kMonitorTailBytes`（24 行 × 8 字节），只折这一段的行（批 3 改口见 §4.3①／②：
  稿初那行「几十行 ≈ 14 µs」是 F5 的折算成本算术，不是屏面容量——14 pt 行高约 20 dp，640 dp 的窗扣掉头三行
  只容得下二十几行），其余 run 折都不折。
- **武装态的常驻代价**：F4 的 0.604 µs / 32 KiB 加一次 `now()`（F11：11 ns 量级），每批一次；
  落地形态是 `record_raw()` 那把**无争用的短临界区**（锁内只取 `shared_ptr` 副本）＋一次空指针判，
  与今天的 `log_` 那条同形；空批（`ingest({}, true)` 的收尾一轮）在取锁前就返回（§4.2②）。

### 9.1 业界形态调研（2026-10-26 检索现行文档与用户报告）

| 产品 | 历史与回溯形态 | 取走的结论 |
|---|---|---|
| Windows Terminal | 历史行数可配（上限 32767）；滚轮离开底部后**不自动吸回**，回底靠滚动条；「自动吸回底部」在用户报告里是缺陷面（往上翻时被新输出拽回，反复抓滚动条才读得成） | 跟尾只能是「贴底才跟」；恢复必须是显式动作（滚到底或一键回底） |
| Tera Term | `MaxBuffSize` 缺省 10000 行、按「行数 × 终端宽 × 5 字节」占内存，写进 `TERATERM.INI` 跨重启；时间戳挂在 Log 设置里 | 容量与时间戳档是「跨会话一致」的量，终要落成设置键（二期不做，见 §9.8）；先让历史可见，再谈可调 |
| Arduino IDE 2 Serial Monitor | 「Autoscroll」与「Show timestamp」是两枚工具栏开关；暂停/恢复也是显式按钮 | 视图侧两枚缺省档继续留面板局部量；「回到最新」必须是一枚随时可按的动作 |
| CoolTerm / SerialTool 一类串口工具 | 十六进制/文本双视图 + 暂停 + 时间戳 + 保存；历史是**连续缓冲**而非分页 | 分页（上一页/下一页）不是这一族的形态；连续缓冲才符合「回看」 |

四条共同指向同一形态：**连续历史缓冲 + 只有贴底才跟尾 + 离底冻结且绝不自动拽回 + 一枚显式回底动作**。
稿 §7 原来那条「形态需要真机手感才能定」与这不矛盾：手感要定的是行高与滚轮步进，不是「冻结还是吸回」
这条硬语义——后者业界的答案已经一致，吸回是缺陷而不是特性。

### 9.3 折算件的新口径

```cpp
// 行号是显示期量，但不是几何量：纯逻辑件仍然不认识像素、不认识 Aurora 类型。
[[nodiscard]] auto monitor_row_count(const std::vector<session::RawRun> &runs,
                                     const MonitorRowOptions &options) -> std::size_t;
[[nodiscard]] auto monitor_row_window(const std::vector<session::RawRun> &runs,
                                      const MonitorRowOptions &options,
                                      std::size_t first_row, std::size_t max_rows)
    -> std::vector<MonitorRow>;
[[nodiscard]] auto monitor_rows(const std::vector<session::RawRun> &runs, const MonitorRowOptions &options)
    -> std::vector<MonitorRow>;  // = window(0, SIZE_MAX)
```

一期的 `monitor_rows` 改成**同一台扫描器的委托**，不再第二份实现：行边界、CRLF 归属、挂起尾段、
末尾不完整行四条口径（§4.1③／§2 的「行边界」「挂起尾段」）只写一遍，`row_count` 与 `window`
的切片一致性由这条委托从结构上保证。扫描器按「段」推进（`memchr` 找 CR/LF），段内按满 8 字节
成行；窗口之前的行只推进计数、不建字符串，故**后段窗口的成本与环总长无关的部分只剩一次线性扫描**。

### 9.4 面板状态机

```
                 ┌──────────── 跟尾（follow）────────────┐
   开卡/清空/回底 │ tick: revision 变才重折；贴底重建时     │
                 │ 以 pending scroll_offset 落到底         │
                 └───────────────┬───────────────────────┘
                                 │ 偏移离开底部（几何判据）
                                 ▼
                 ┌──────────── 冻结（frozen）─────────────┐
                 │ 不读环、不重建；标题区出「已暂停跟尾」   │
                 │ 与「回到最新」；仅在窗口滚出折带时重折   │
                 │ 并保持偏移（deserialize pending offset）│
                 └───────────────┬───────────────────────┘
                                 │ 滚回底部 / 点「回到最新」
                                 ▼
                              跟尾（回底即重读环）
```

- **判据只有一条**：`list->max_scroll_offset() > 0 && list->scroll_offset() < max - 0.5` ⇒ 冻结。
  未布局的列表 `max == 0`，一律视为跟尾（否则每次重建后的第一帧都会误判成「离底」）。
- **暂停**是第二枚闸：`paused_ || frozen_` 都不读环。暂停中滚到底**不会**自动恢复（开关仍是关的）；
  点「回到最新」会同时清掉暂停与冻结。
- **窗口重折**：冻结态每帧看 `visible_range()`，可见区（含 `cache_extent`）逼近折带边缘（余量 < 4 行）即
  以可见首行为锚重折 96 行，经 `deserialize_props({"scroll_offset": <当前偏移>})` 在原偏移上重建。
  跟尾态不重折——数据一变就整卡重建，窗口恒取末尾 96 行。
- **重建时机仍只有 `tick()`**（一期 §4.3③ 的纪律不变）：两枚开关、清空、冻结边沿只置
  `rebuild_pending_`，真正折行与装浮层都在帧边界。

### 9.5 数字与代价

- 折行：跟尾只折末尾 96 行（**实测 ≈ 17–19 µs**，2026-10-26 批 A 后一次性探针，MSVC `/O2`；设计期按
  F5 估的 23 µs 在同一档）。**但窗口 API 还要一次「数到 `first_row`」的线性跳扫**：整环（2000 run
  ≈ 12000 行 ≈ 满 256 KiB）取末尾 96 行实测 **≈ 136 µs**，其中 ≈ 95 µs 是跳扫、≈ 19 µs 才是折行——
  成本随**环长**走而不是随窗口走，稿面原先写的「≈ 23 µs」只覆盖了折行那一段，偏差 6 倍，按 §9.9
  的复核条款就地回写。冻结重折一次同量。
- 计数：256 KiB 线性扫描（`memchr` 找行尾），每帧至多一次；同规模实测 **≈ 95 µs**；跟尾帧因此是
  「计数 + 跳扫 + 折行 ≈ 230 µs + 快照拷贝 ≈ 5 µs」（满环、`/O2`，约一帧 16.7 ms 的 1.4%），
  `revision` 未变时全为零（D17）。仍远低于「32768 行全折」的 ≈ 7.8 ms/帧。
- 快照：每跟随帧一次 `RawTap::snapshot()`（≤ 256 KiB 拷贝，F4 折算约 5 µs）——一期已有，本期不增。
- 内存：环 256 KiB + 面板折带 96 行字符串（≈ 96 × 60 B）+ `LazyList` 可见项（约 37 行控件）；
  没有 32768 行的控件树。

### 9.7 Aurora 缺口（任务书候选，按「可组合能力留本仓」分流）

1. **`LazyList` 无可刷新已实例化条目内容的公共 API**。`set_item_builder` / `set_count` 只影响新进入窗口的
   条目，存活条目继续显示旧内容（`maybe_restore_scroll` 同族的惰性口径）。本仓替身：整卡重建
   （`refresh_overlay()`），代价是每次数据变化重建一次浮层与可见行控件；在监视卡的量级（每帧至多一次、
   可见项几十）可接受。框架侧建议：`invalidate_items()` 或 `ItemBuilder` 带 revision 的刷新语义。
2. **`LazyList` 无「锚定到末尾」的公共入口**。唯一能在首次布局后落到底的通路是
   `deserialize_props({"scroll_offset": <极大值>})`（`pending_offset_` 在视口已知后夹取）。本仓替身即此；
   每次跟尾重建传一次 JSON 对象。框架侧建议：`set_scroll_anchor(End)` / `set_pending_scroll_offset()`。
3. **`LazyList` 无滚动位置变化回调**。冻结/恢复靠 `tick()` 轮询 `scroll_offset()` 与 `max_scroll_offset()`；
   帧驱动在滚动期间是热的，故判据成立，但「滚到底那一帧立刻恢复」依赖下一帧的 `tick()`。框架侧建议：
   `set_on_scroll_changed(std::function<void(float)>)` 或复用 `offset_signal()` 的订阅面（已有，但面板在
   `tick()` 里比较更便宜）。三条都只登记为任务书候选，不改 Aurora。

### 10.5 数字与代价

- 满环（256 KiB）在 8 字节档折成 **32768 行**，行文本 **1,802,239 字节 ≈ 1.72 MiB**。全折一次的成本
  本机实测（一次性探针 `dump_probe`，不入仓，2026-10-26 MSVC `/O2 /std:c++20`，直接编
  `src/ui/serial_monitor_format.cpp`，20 次取均值、先预热一次）：**9.427 ms／次 = 0.288 µs／行**；
  时间戳档关掉是 **8.245 ms = 0.252 µs／行** ⇒ `localtime` + `strftime` 那一档的净成本 ≈ **1.2 ms**（占 12%）。
  与 §2 那条 F5 的 0.239 µs／行推算（7.8 ms）同一量级、略高 21%——差在整份串要一次 grow 到 1.8 MB。
  ⇒ 一期那条「只画 24 行」的顶棚之所以必要，这里有了实测成本面：**满环全折 ≈ 10 ms**，
  是一次点击的量级，不是一帧的量级。
- 它发生在**点击派发**而不是 `tick()`：与「事件回调不做长计算」（§4.5 第 25 条）的关系按 `SettingsPanel::run_export()`
  同一条口径判定——一次性、用户显式发起、量级毫秒而不是秒，且紧随其后的是原生对话框与写盘（那两条本来就是阻塞 IO，
  已建立的先例比本件更重）。**不做**后台线程 + 有界队列那一套：那是给持续热路径准备的，给一次点击加线程只会引入
  「文本在途时屏面又变了」的新口径问题（与 D20 直接冲突）。
- 复制一份 1.8 MB 文本进剪贴板是本机 OS 的行为，未测；若真机上明显卡，代价面记在走查清单而不是自动判据里。

### 10.6 走查清单（AGENTS §4.4 第 33 条，人工）

1. 复制：满环量级下按下是否有一次明显停顿；粘到编辑器里行数与屏面尾行是否对得上。
2. 导出：原生保存框标题与过滤器读起来是否像「导出串口转储」；文件名缺省值是否合适（本期不合成缺省名，见 §10.7）。
3. 导出成功后那句留痕里的长路径在 640 dp 卡里是否截断得能看懂。
4. 换掉一个已存在的文件：OS 弹「替换？」→ 同意后旧文件确实整体换新，且权限位仍只我可读。（「整体换新」
   已由 `utest_file_secure::the_second_write_replaces_the_target_whole` 锁住；**Windows 的继承 ACL** 这条
   只有真机看得出，`create_private_file` 的 Win 腿本就不改 ACL。）
5. 写到只读目录（如 `C:\Windows`）：上屏那句失败、临时件不留。（失败姿态的自动化版本是
   `a_refused_or_broken_write_never_moves_anything` 的「父目录不在」那一档；只读目录是另一条现场。）
6. 暂停中导出：文件末行应与屏面最后一行一致，而不是环里更新的字节（D20 的人眼验证）。
7. 改口那句常驻声明在小窗宽下是否仍完整可读——它是 D23 那第四道确认的替代品，被截掉就等于没有。
8. 在对话框里点一个**中文名**的目标（如 `桌面\串口捕获.txt`）：落盘后文件名应与点下的逐字一致、目录里
   不多出一份 0 字节的 `.tmp`（F15 那条读数的现场复核；`utest_file_secure` 已有同判据的自动例，
   但那条走的是本仓 temp 目录，不是真实桌面路径）。

## 11 四期：文本视图（D26–D35，2026-10-26 自裁）

§10.7 在册第一条「按会话编码解码的文本视图档」的这一棒。要解决的问题很直白：这块卡今天只有十六进制——
设备吐一段日志（`AT+OK\r\n`、模组的 boot log、仪表的 CSV 行流），用户要在屏上读出它说了什么，
得自己在脑子里做 UTF-8/GB18030 反解；而这份字节**已经**被会话按 `terminal.encoding` 解过一遍并画进了终端，
卡上却只给字节。延后它不是因为难，是因为一期把「行形态的算术」定在了字节上（D5①）。

### 11.1 业界形态调研（2026-10-26 检索现行手册与产品页）

- **RealTerm** 的显示模式是**面板局部**的一枚「Display As」选择器，取值 ASCII／Hex／Hex+ASCII 等组合，
  切档不改采集本身；另有「Capture As HEX」——落盘格式与屏上格式是**两个独立维度**
  （`serialtalks.com/realterm`、SparkFun《Serial Terminal Basics》的 RealTerm 段）。
- **Tera Term** 的十六进制显示走 **debug 模式**（Shift+Esc 进，收到的每个字符连同控制码全部上屏），
  手册把它列在「终端仿真」设置族里而不是日志设置族里（`teratermproject.github.io/manual/4/en/setup/teraterm-term.html`）。
- 两者共同点：**视图档属于那块视图，不属于全局配置**；且**都保留一份「不可打印字符也上屏」的显式选择**，
  而不是把它们画成看不见——看不见就等于说谎。差异点：RealTerm 允许 Hex 与 ASCII **同屏并列**，Tera Term 是二选一。

结论取**二选一的切档**（本卡的行宽算术只容得下一种行形态：hex 档一行 54 字符已经把 640 dp 卡宽用满，
Hex+ASCII 同屏等于回到 D5③ 否掉的 16 字节档）。

### 11.3 屏面与词条

开关行第三枚：`serial.monitor.toggle.text_view`（与既有 `…toggle.timestamp`／`…toggle.pause` 同族）。
文本档的一行 = `[HH:MM:SS.mmm] ` + `RX`/`TX` + 两空格 + 解码文本；三段形态与 `MonitorRow` 完全同构，
故 `build_row()` 的强调色（只吃 `direction_label`）与等宽族纪律一字不改，`visible_rows()` 的观测面也不改类型。
尾栏那对竖线在文本档不出现——那是 hex 段的界，文本段的界是行尾本身（画进 `dump` 字段，仍是同一台机器）。
标题行的字节计数与「已丢弃 N 字节」那句留痕在两档同值：它们说的是**环**，不是视图。

### 11.4 判据面

⑴ **D31 只在窗口腿上成立，在全折腿上反过来**。文本档每次窗口折比 hex 档贵 **0.24 ms**（UTF-8，+53%）
到 **1.42 ms**（GB18030，+4.1 倍），多出来的正是「窗口之前那十万字节仍要过解码器推半字状态」——
计数腿只 0.24 ms，窗口腿 0.70 ms，而按行单价折算 96 行建串只 ≈0.045 ms，故中段那 ≈0.4 ms 是解码而不是建串。
但**全折**文本档反而比 hex 档**便宜一半以上**（4.78 vs 10.19 ms）：行少 3.5 倍、产出串小 4 倍，
省下的建串与内存搬运超过了 decode（UTF-8 那条腿本身就是「校验 + 拷码点」，换 GB18030 才多花 1.16 ms）。
⇒ 结论是「文本档贵在每次重画、不在一次取出去」，与 D31 的取舍（保留一台扫描器）不冲突，但稿面那句
「文本档比 hex 档贵」按本条读数就地收窄为**窗口腿**。

⑵ **一帧预算判得住**：`follow_frame()` 只在 revision／档变时折一次窗口，文本档最贵的读数 **1.87 ms ≪ 16.7 ms**，
且这段发生在 `tick()` 而不是绘制路径 ⇒ 不触 AGENTS §4.5 第 25 条。GB18030 那一档是上界（逐码点走 OS 转换表）。

⑶ **导出腿的量级不改判**：满环全折文本档 4.78 ms 低于三期实测的 hex 全折（9.4–10.2 ms），
仍是「一次点击的量级」，§10.5 那句「一次性、用户显式发起、后面跟着原生对话框与写盘」的判定不需要重议。

### 11.6 走查清单（AGENTS §4.4 第 33 条，人工；在 §10.6 八条之上加五条）

1. 串口会话吐一段人读的日志（AT 回应或 boot log），拨到文本档：**那一屏读得下来**，中文档（GB18030）不乱码。
2. 文本档与 hex 档来回切两次：字节计数、丢弃留痕、绑定名都不变（只有行形态变）。
3. 文本档里点复制／导出：剪贴板与文件里是**文本**（不是 hex 段），行数与屏面逐行相符。
4. 一段二进制（含 0x00 与 0x1B）在文本档显示成点而不是消失，且 U+FFFD 出现在编码不匹配处。
5. §10.6 第 8 条（F15 那条码页读数的现场复核）照旧。

`.bin` 原始字节导出；三型接入之外的第五型（本仓只有四型）。

### 12.7 走查清单（AGENTS §4.4 第 33 条，人工；在 §11.6 五条之上加四条）

1. 本地标签（PowerShell／WSL）开卡：RX 里看得见应用写出的**原始 VT 字节**（含 `ESC[`），文本档与 hex 档都读得下来。
2. SSH 标签开卡：绑定那格是 `档案名 · user@host[:port]`，缺省端口不出现；同一标签分屏后开卡，看到的是**焦点那一格**
   的字节，另一格的输出不出现在卡上。
3. Telnet 标签开卡：绑定那格是 `host[:port]`；协商字节（`IAC` 那串）在 hex 档里看得见、文本档里折成点而不是消失。
4. 旧键位兼容：在配置里手写一条 `serial.monitor.toggle` 的覆盖，启动后它应当作用在新 id 上（只读表里**不出现孤儿行**）。
